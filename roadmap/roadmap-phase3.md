# Phase 3: Consensus (MCDD Semantic Consensus Layer) Design Document

## 🎯 Core Objectives
Break through traditional text-based line comparison (Text-based Diff) merge methods by utilizing AST (Abstract Syntax Tree) to understand semantic code changes. Filter out "noise divergence" caused by spaces and indentation, and when true logical conflicts arise, use model consensus algorithms (Model-Consensus Driven Development) for automatic arbitration.

## 🏗️ Architecture Design & Technology Stack

### 1. Cross-Sandbox Diff Extraction Module (`diff`)
*   **Responsibility**: Extract change sets from all completed Git Worktrees as inputs for the consensus engine.
*   **Mechanism**: Perform operations akin to `git diff HEAD` for each sandbox, extract patch file contents, and categorize them by modified files.

### 2. AST Semantic Filtering Engine (`semantic`)
*   **Responsibility**: Compare code generated by different Agents to determine if they are logically equivalent.
*   **Dependencies (Crates)**: `tree-sitter` along with language-specific parsers (like `tree-sitter-rust`, `tree-sitter-go`).
*   **Operating Principle**:
    *   Parse the modifications to the same file from two sandboxes into separate abstract syntax trees.
    *   Traverse the syntax trees, compare node structures and key identifiers, and ignore irrelevant nodes like `whitespace`, `comment`.
    *   If two pieces of code have different text but equivalent AST nodes and logical paths, they are determined to have "no semantic conflict," and one is directly adopted.

### 3. MCDD Arbitration Strategy Engine (`consensus`)
*   **Responsibility**: Decide which code to adopt or how to merge the code when genuine semantic divergence occurs.
*   **Strategy Implementation**:
    *   **Majority Vote**: If 2 out of 3 Agents provide the same or semantically equivalent modifications, adopt the majority.
    *   **Cross-Review**: Draw a new (or high-weight, like Architect) Agent as a referee. Feed the differences of both sides (Diff A vs Diff B) to it, allowing it to decide which one to adopt.
    *   **Referee Arbitration**: Hardcode in `.mace.toml` that, when conflicts occur, unconditionally take the code of a specific role (like `senior-coder`) as the standard.

### 4. Human-In-The-Loop Deadlock Resolution (`hitl`)
*   **Responsibility**: Prevent models from falling into endless loops of invalid debates.
*   **Mechanism**:
    *   Define `max_rounds` (default e.g., 3 rounds).
    *   If no successful merge is observed in the TUI after exceeding the rounds, the FSM enters the `HITL_Pending` state.
    *   Display the divergent code side-by-side in the TUI interface, popping up options for developers to manually intervene and choose (`Accept A`, `Accept B`, `Abort`).
